# CodeWhale Agent 运行时 — 一个持久化基板，熟悉的启动方式

本文档解释子 agent、无头 `exec` 路径和 Agent Fleet 之间的关系。它们此前已演变成*两个*并行的"worker"系统，修复方案是使 **fleet 支持的 worker 运行**成为持久化原语。"子 agent"作为嵌套角色的产品词汇仍然有用，但它不应暗示一个具有较弱生命周期语义的独立执行基板。本文还回答了 #2972 中悬而未决的方向问题（"与 Claude Code 多大程度的趋同是合适的？"）。

## 核心理念

有且仅有**一个**东西来运行分离的 agent 工作：一个包装在持久化 worker 生命周期中的**无头 agent 运行时**。它是一个模型循环，拥有完整的（策略门控的）工具界面，并且可以通过相同的生命周期委托子工作。其他所有东西都只是*启动*该运行时的不同方式，或者*观察*它的不同方式。

```
                         ┌───────────────────────────────┐
                         │     无头 agent 运行时           │
                         │  （完整工具 + 可子派生）         │
                         └───────────────────────────────┘
                            ▲             ▲             ▲
            启动方式  │              │              │ 启动方式
                     │              │              │
        ┌────────────┴───┐  ┌───────┴────────┐  ┌──┴───────────────────┐
        │   TUI 对话      │  │ `codewhale     │  │   Agent Fleet         │
        │  （交互式，      │  │   exec`        │  │  （持久化：账本、      │
        │   进程内）       │  │  （无头 CLI，   │  │   调度器、SSH、        │
        │                 │  │   任何人/任何   │  │   告警）— 每个 worker  │
        │                 │  │   时间）        │  │   启动                 │
        └────────────────┘  └────────────────┘  │   `codewhale exec`      │
                                                 └───────────────────────┘
```

- **子 agent** 是面向用户的*带角色的嵌套任务*名称（`explore`、`review`、`implementer`、`verifier` 等）。它应该由与 fleet 相同的 worker 运行生命周期来支持。`agent` 是面向模型的启动器，而非第二个运行时。
- **`codewhale exec`** 是无头前门：任何人都可以随时使用（CI、脚本、另一个 agent），拥有完整工具，发出 `stream-json` 事件流，并且可以派生子 agent。它是*那个*运行时加上一个 CLI。
- **fleet worker** 就是 fleet 启动并持久跟踪的一个 `codewhale exec` 运行 —— 本地作为子进程运行，或远程作为 `ssh host … codewhale exec …` 运行。fleet 不会重新实现执行逻辑；它在*同一个运行时之上*添加了**编排**（持久化账本、调度/租约/重试、主机传输、告警升级）。

因此"fleet vs 子 agent"不是两个类别。它是**同一个无头运行**：Fleet 是持久化控制平面，而子 agent 是嵌套 worker 的角色/UX 词汇。

## 切换规则

如果一个分离的 `agent` 子进程可能因一次性 provider 超时而失败且无重试，而等效的 fleet worker 会重试并保留账本证据，那么切换就是不完整的。将此视为 CodeWhale 运行时的缺口，而非正常的"子 agent 行为"。

兼容性 `agent` 运行时现在对瞬时性 provider 头、流和超时失败进行退避重试，然后再将 worker 标记为中断；当重试耗尽时，它会保留检查点并返回续接句柄。剩余的趋同工作是使该生命周期在进程重启、远程执行和完整的 fleet 账本调度中保持持久化。

目标规则是：

- 持久化或长时间运行的工作通过 fleet worker 生命周期进行；
- `agent` 应将工作入队或观察 fleet 支持的 worker 运行，而不是拥有独立的生命周期；
- 进程内子进程仅作为小型兼容性/延迟优化允许存在，并且它们必须暴露与 fleet 路径相同的终端状态、重试语义、回执和检查句柄。

在产品语言中说"打开一个子 agent"是可以的。在架构语言中，这意味着"以此角色启动一个嵌套 fleet worker"。

## 为什么是这种形态（以及它为什么修复了延迟问题）

动机问题：派生许多进程内子 agent 导致 TUI 延迟，因为每个子进程都会克隆一个重量级运行时并重建整个工具注册表，*并且* TUI 会为每个子进程渲染完整的卡片/转录。

调查 Claude Code、Codex 和 Kimi，使编排器在高扇出下保持轻量的因素**不是**进程边界 —— 三者都在进程内运行子 agent。它是**隔离 + 紧凑事件流**：

- 子进程的转录**永远不会**回流到父进程 —— 父进程获得结果摘要和一个小型生命周期事件流；
- UI 渲染**计数**（`2 running / 3 done`），而不是每个 worker 一个子会话；
- 每个 worker 的工具界面直接从**角色/能力配置文件**构建，而不是"构建所有然后过滤"。

因此，"无头"意味着*执行形态不像 UI* —— 它**不**意味着更少的能力。无头 worker 保持完整的工具集，并且可以派生子 agent。

当工作还需要**持久化**（在 TUI 关闭、笔记本休眠后存活）或**远程**（SSH）时，fleet 将 worker 作为 `codewhale exec` 在进程外运行。重量级构造完全在另一个进程中，因此无论扇出如何，编排器都保持流畅，并且运行可以在重启后存活 —— 这是 #3154 的日级自治目标。

## 一个递归轴

worker 在 `spawn_depth = 0` 运行，并且可以在 `spawn_depth + 1 ≤ max_spawn_depth` 时派生子进程，因此预算 `N` 提供 `N` 级嵌套委托。子 agent 和 fleet worker 共享**一个**轴，源自 `codewhale_config`：

- `DEFAULT_SPAWN_DEPTH = 3` —— 独立子 agent 和 fleet worker 的默认预算（因此它们不会漂移为"两个移动目标"）；
- `MAX_SPAWN_DEPTH_CEILING = 8` —— 每个配置值（fleet `max_spawn_depth`、`agent` 的 `max_depth`）都会钳制到此上限。

根 worker 即使在预算为 0 时也始终运行；预算门控的是*子进程*委托。默认值至少允许三级嵌套。

## 事件词汇

fleet 账本持久化 worker 自身的事件流，而非一个独立的模拟分类法。`codewhale exec --output-format stream-json` 发出 `{"type": "content" | "tool_use" | "tool_result" | "metadata" | "done" | "error"}` 行，映射到 fleet 账本的 `FleetWorkerEventPayload`（`RunningTool`、`Running`、`Completed`、`Failed` 等）。一套词汇，两个界面。

## 与 Claude Code 的趋同 (#2972)

CodeWhale 应在**形态**上与 Claude Code 趋同，而非品牌：

- **采纳**：具有真正 CLI/SDK 前门的无头运行时；子 agent 作为返回摘要（而非转录）的隔离运行；紧凑的、事件驱动的扇出投影；能力/角色工具配置文件；技能生态系统（#2743）；结构化运行回执。
- **保持不同**：CodeWhale 品牌和一流的 DeepSeek/GLM/MiniMax/多 provider 支持；本地优先的 **Agent Fleet**（持久化、支持 SSH 的编排）作为 CodeWhale 在共享运行时之上的自有层；Workflow 作为编排覆盖层。
- **不要**按界面分叉执行语义。TUI、`agent`、`exec`、运行时 API 和 fleet 都必须驱动*同一个*运行时并观察*同一个*事件流 —— 那里的分歧正是产生"两个移动目标"的原因，而本文档的存在就是为了防止这种情况。

对任何新 agent 界面的试金石测试：*它是启动并观察那一个运行时，还是发明了第二个？*只允许前者。
